## T8 — Stopping a recording hangs

> "when you go to end the recording, it just hangs there. If it absolutely,
> 1000% needs time to load, just throw in a loading screen but first try to
> optimize it for speed like you did with the beginning previously."

### Order of work — optimise first, spinner second

A spinner is the fallback, not the fix. Only add one for work that provably
cannot be removed from the blocking path.

### Jeff's decisions (2026-09-17, asked before an unattended run)

- **Background publication is approved.** "Give me the screen back instantly,
  finish filing in the background." The audio file may land in the Tangent
  folder seconds after the UI returns, provided the recording is durably stored
  and appears in the app immediately.
- **If a wait is irreducible: stay on the recording screen** with a labelled
  indicator ("Saving recording…"), not a bare spinner and not an early
  navigation.
- Test recordings created for measurement may be deleted automatically. Jeff's
  own recordings are never touched.

### Why the earlier "0.3s" reading was wrong

Stop-to-persisted-row was measured at 0.3s during iteration 3 and reported as
"save was never slow". That measurement timed the **database row appearing**,
not the moment the UI became usable again.

This is the same error that hid the 8-second record delay: a stage timer was
measured instead of the human experience. The record delay was only found by
tapping at a realistic moment and counting, exactly as Jeff did.

**Measure what the user feels: finger leaves the stop button → screen is
interactive again.** Screenshot sampling at 500ms, or an in-app stage timer that
ends at first frame of the next screen. A DB timestamp is not the finish line.

### Where to look — the awaited chain

`RecordingController.stop()` (`recording_controller.dart:84`) awaits
`stopAndPersist()` (`recording_coordinator.dart:158`), which awaits, in order:

1. `_recorder.stop()` (:171) — native encoder finalisation.
2. Result validation against the reservation (:180-189).
3. `_mutations.serialize(...)` → `_persistence.save(...)` (:192-195) — the
   suspect. Inside it: `_completeCapture` (`recording_persistence.dart:374`)
   and `_publishAndCommit` (:620), which run **multiple `_checkpoint` writes**
   (:385, :396, :426, :454, :530) plus `publishPreparedCapture` (:499).

Each `_checkpoint` is a journal write + DB transaction + readback (:333-366).
On SAF, `publishPreparedCapture` copies the staged file into the user's chosen
folder — that is a full audio-file copy over SAF, and a strong candidate for the
visible hang on longer recordings.

### Prime suspects, in order

1. **SAF publish copy on the blocking path.** A 5-minute recording is several MB
   copied through SAF before the UI is released. Scales with recording length —
   consistent with "it just hangs there" on real recordings but not on the 6s
   test clips.
2. **Serialised checkpoint writes.** Five-plus journal+transaction+readback
   round trips, each cheap alone, awaited in series.
3. **Navigation waiting on the whole chain** rather than on the durable commit.

### Constraint — durability is not negotiable

The journal and checkpoints exist so a recording survives a crash or a force
stop mid-save. **Do not make the save fire-and-forget.** The audio must be
durable before the UI reports success.

The legitimate move is to release the UI once the recording is **safely
committed**, and let slower non-essential publication continue in the
background — the same split that fixed the record path (`31645e8`), where the
question being answered was made cheap rather than the answer being skipped.

If publication must be deferred, the recording must still appear correctly in
the list, and a crash before publication completes must leave it recoverable.

### Acceptance

- Measured finger-off-stop → interactive, on a **realistic recording length**
  (test 5+ minutes, not 6 seconds), before and after.
- No regression in the record-start path (~1s, `31645e8`).
- `recording_staging_validation_test.dart` and
  `recording_cleanup_committed_test.dart` stay green and unmodified.
- Kill the app mid-save; the recording is still there and intact.
- Only if irreducible work remains: a loading indicator that states what is
  happening, never a bare spinner.

## T9 — Line eraser on the pen screen

> "there needs to be a line eraser built into the pen screen"

### Current state

`notebook_editor_screen.dart` holds `List<InkStroke> _strokes` (:70), loads from
`notebook.ink.strokes` (:133), saves via `NotebookInk` (:292), and exposes
**undo only** — `undoLastStroke()` behind an `Icons.undo` button (:481-483).
Undo is last-stroke-only, so fixing an early mistake means destroying
everything drawn after it.

### What to build

A **stroke eraser**: tap or drag a stroke to delete that whole stroke. Not a
pixel eraser — strokes are the stored unit (they round-trip through the durable
notebook file), so removing whole strokes keeps the file format unchanged.

- **Both gestures** (Jeff's decision): tap a line to delete that line, and
  drag across several to wipe them as you go.
- A tool toggle (pen / eraser) beside the existing undo button.
- Clear indication of which tool is active — this is a mode, and an unlabelled
  mode is how you end up erasing when you meant to draw.
- Eraser deletions go through the same undo history as drawing; an accidental
  erase must be undoable.
- Erasing marks the notebook dirty and saves like any other edit.
- Hit-testing needs a tolerance band around thin strokes — exact-pixel hit
  testing on a 2px line is unusable with a fingertip, and should be forgiving
  with a stylus too.

### Acceptance

- Erase a stroke drawn early without touching later strokes.
- Erased strokes stay erased across save → close → reopen.
- Undo restores an erased stroke.
- Round-trips through the durable notebook file (the uninstall/reinstall test
  that proved 94 ink points survive).
- Switching tools never loses in-progress work.
