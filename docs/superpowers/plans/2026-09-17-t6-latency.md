# T6 — Startup and capture latency

**Branch:** `feature/text-note` · **Date:** 2026-09-17

Jeff: *"We really, really need to speed up the speed at which the recording kicks
in, the speed at which items save, the whole lot. The entire app is feeling
sluggish. It needs to be able to launch, then record immediately since that is
the main function of the whole app really."*

## Measured baseline (device REDACTED_DEVICE, 39 dumps, 65-file folder)

| Metric | Measured |
|---|---|
| Cold `am start -W` TotalTime | **851 ms** (fine) |
| Tap record at t+1.7s → timer moves | **never within 21 s** |
| Notebook adoption after launch | ~20 s (was ~150 s before `b50db49`) |

Launching is fast. The *app* is not usable for ~20 s after launch.

## Root causes (read from source, not guessed)

1. **Record is gated on full storage bootstrap.**
   `recording_controller.dart:52` does `await _ready()` where `_ready` is
   `() => ref.read(storageBootstrapProvider.future)`
   (`recording_controller.dart:141`). Bootstrap does legacy re-adoption of every
   recording in the folder plus capture recovery. Until that whole future
   completes, `start()` is parked and the UI sits in `starting` — the tap looks
   swallowed.

2. **`legacy_restore` is never cleared.**
   `grep legacyRestore lib/` matches only generated Drift code. Nothing in
   `lib/` ever sets it back to false. So the legacy adoption sweep of all 39
   recordings re-runs on **every launch, forever** — it is supposed to be a
   one-shot migration.

3. **Bootstrap is one monolithic future.** Capture recovery, legacy adoption and
   notebook import are sequenced together, so the slowest member gates the
   fastest consumer. Recording only needs a writable staging dir and a capture
   fence — not a folder scan.

## Work items

### T6-A — Record without waiting for the folder scan
Split bootstrap into `captureReadyProvider` (staging dir + fences + owned
capture recovery — everything `start()` genuinely needs) and
`catalogSyncProvider` (legacy adoption, notebook import, folder enumeration).
`start()` awaits only `captureReadyProvider`. Catalog sync continues in the
background and must never block capture.
**Acceptance:** a test proves `start()` completes while catalog sync is still
pending; on device, record tapped ~1 s after cold launch shows a counting timer
within 2 s.

### T6-B — Make legacy restore one-shot
Clear `legacy_restore` for a location once its adoption sweep completes without
unresolved entries, so the O(n) folder scan stops running on every launch.
Must remain correct if adoption partially fails (leave the flag set), and must
not re-adopt rows a user deleted.
**Acceptance:** RED test showing the sweep re-runs on second bootstrap; GREEN
showing it runs once. Device: second launch does no adoption work.

### T6-C — Save latency
Measure and reduce time from Stop → row visible and from note Save → detail
screen. Report the measured before/after; do not weaken durability guarantees
(the write-temp/verify/replace publish order stays).

## Non-negotiables

- No data loss, no weakened durability, no fabricated speed claims.
- Every number reported must come from a real measurement.
- Full `flutter test` + `flutter analyze` green before any commit.
- Frozen: `recording_staging_validation_test.dart`,
